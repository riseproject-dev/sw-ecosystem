## 1. Project Overview

Edge Impulse Inferencing SDK (C++) is a portable, source-vendored C++ library for digital signal processing and machine learning inference on embedded and edge devices, distributed as the `edgeimpulse/inferencing-sdk-cpp` GitHub repository. It contains the on-device implementation of processing and learning blocks generated by the Edge Impulse Studio platform, and is meant to be symlinked or vendored into a consuming firmware/application project rather than built or installed standalone, per the repository's own [README](https://github.com/edgeimpulse/inferencing-sdk-cpp/blob/master/README.md): "If you want to develop locally the easiest is to grab the example-standalone-inferencing... example applications... then symlink this repository in."

**Governance:** There is no independent governance body. This is a corporate SDK owned by Edge Impulse Inc., which was acquired by Qualcomm Technologies, Inc. in March 2025. The repository has no MAINTAINERS, OWNERS, GOVERNANCE, PLATFORMS.md, SUPPORT.md, or CONTRIBUTING.md of its own; the only such files present are vendored third-party ones (`porting/espressif/ESP-NN/CONTRIBUTING.md` from Espressif, `porting/ethos-core-driver/SECURITY.md` from Arm). The repo functions as a largely one-way squash-mirror of Edge Impulse's internal monorepo: of 136 total commits, 63 (the entire recent history, all "SDK version" bumps) are pushed by an automated bot account, `edgeimpulse-firmware-uploader[bot]`, with no visible individual PRs or review trail on GitHub.

**Corporate maintainers** (all Edge Impulse/Qualcomm employees, by commit count): Jan Jongboom (Edge Impulse co-founder/CTO, 50 commits), Mateusz (`mateusz@edgeimpulse.com`, 16), Yan (`yan@edgeimpulse.com`, 3), Ross (`ross@edgeimpulse.com`, 1), Arjan Kamphuis (2), and one external/customer contributor, Raul (`raul@nobi.io`, 1). There is no independent or external maintainer group.

**License:** BSD-3-Clause-Clear for Edge Impulse's own code, with vendored third-party components under their own licenses (CMSIS: Apache-2.0; TensorFlow: Apache-2.0; kissfft: BSD-3-Clause; ESP-NN: Apache-2.0; ethos-core-driver: Apache-2.0; gemmlowp/flatbuffers/ruy: Apache-2.0).

**Community culture on new ports:** No formal tiering or acceptance process is documented. Edge Impulse's public docs (`docs.edgeimpulse.com/reference/inferencing-sdks/cpp-inferencing-sdk`) state, regarding the `config.hpp`/`numpy.hpp` target-optimization hooks: "If you want to add optimizations for a new target this would be a good place to start. We welcome contributions!" - the only public invitation found; no CODEOWNERS gating or documented review workflow exists in the repo itself, consistent with its role as a mirror of an internal monorepo.

## 4. Technical Architecture and RISC-V-Specific Subsystems

The SDK contains several architecture-specific acceleration subsystems. None has a RISC-V-specific implementation.

| Component | arm64 (Cortex-A/NEON) | Cortex-M (CMSIS-NN/DSP) | x86_64 | riscv64 |
|---|---|---|---|---|
| Hand-tuned NN kernels (CMSIS-NN) | full | full | scalar fallback | **missing** |
| Hand-tuned DSP/math kernels (CMSIS-DSP) | full (NEON path) | full | scalar fallback | **missing** |
| SIMD vector intrinsics (`__ARM_NEON`/`__aarch64__` in 3 files) | partial | n/a | incidental only (4 files, inherited from upstream kissfft/TFLite, not EI-authored) | **missing (zero RVV intrinsics found anywhere, including vendored ruy/gemmlowp/TensorFlow trees)** |
| Named `porting/` target directory | n/a (covered generically) | via mbed/stm32-cubeai/etc. | n/a | **missing (no `porting/riscv*` directory among 26 named ports)** |
| CI / build validation | none (no CI exists) | none (no CI exists) | n/a | **missing (no CI of any kind in the repo)** |

**Dispatch logic** (`classifier/ei_classifier_config.h`, `dsp/config.hpp`): acceleration macros such as `EI_CLASSIFIER_TFLITE_ENABLE_CMSIS_NN` and `EIDSP_USE_NEON` are set to 1 only when the compiler defines ARM Cortex-M target macros or `__ARM_NEON`/`__aarch64__`. Every other architecture, including riscv64, silently falls through to the generic portable C++ scalar reference implementation. There is no `#error` on unrecognized architectures and no riscv64-specific branch anywhere in the source tree.

**Only RISC-V-adjacent code found** (2 files, both third-party vendored, not Edge-Impulse-authored):
- `porting/espressif/esp-dsp/modules/common/include/dsp_common.h` - `#if defined(__XTENSA__) || defined(__riscv)` (cycle-counter macro selection for Espressif's RV32IMC-based ESP32-C3/C6 chips)
- `porting/espressif/esp-dsp/modules/common/include/dsp_platform.h` - identical guard for `esp_cpu.h` inclusion

These are 32-bit embedded-target compiler guards inherited from Espressif's vendored `esp-dsp` library, unrelated to riscv64/Linux and unrelated to any acceleration path - they only affect which cycle-counter intrinsic is called.

**ESP32-C3 note:** `dsp/config.hpp` (line 114) and `classifier/ei_classifier_config.h` (line 85) both list `CONFIG_IDF_TARGET_ESP32C3` (an Espressif RISC-V chip) among the macros that enable `EIDSP_USE_ESP_DSP`/`EI_CLASSIFIER_TFLITE_ENABLE_ESP_NN`, but the actual hand-written assembly kernels under `porting/espressif/ESP-NN/src/**/*.S` and `porting/espressif/esp-dsp/modules/fft/**/*.S` (27 `.S` files total) are all suffixed `_esp32s3`/`_aes3`/`_ae32`/`_arp4` - Xtensa-only. There is no `_esp32c3`/RISC-V-variant kernel; ESP32-C3 builds fall through to the plain portable C/C++ reference implementation with no ISA-specific optimization even on that RISC-V target.

## 13. Readiness Assessment

- **Color:** orange (no upstream CI of any kind, no distro/third-party package, no GitHub releases for any architecture)
- **Release provider:** none
- **Optimization level:** absent - the SDK contains hand-tuned SIMD/assembly acceleration for ARM (CMSIS-NN/DSP, NEON) and Xtensa (ESP-NN), but zero RISC-V-specific optimized code exists anywhere in the tree (no RVV intrinsics, no `arch/riscv/` directory, no `.S` assembly files for RISC-V). riscv64 falls through to the generic portable C++ scalar reference implementation, identical to any other unlisted architecture. ISA extensions that would close the gap: RVV (vector NN/DSP kernels analogous to CMSIS-NN/NEON paths) and, secondarily, Zba/Zbb for scalar bit-manipulation speedups in the reference kernels.
- **Justification:** The repository has no `.github/workflows` directory and no CI configuration of any kind ([repository tree at HEAD `7e1cb5747f4b87e2e59a12c907e2a35c929008c2`](https://github.com/edgeimpulse/inferencing-sdk-cpp)), publishes zero GitHub releases for any architecture ([releases page](https://github.com/edgeimpulse/inferencing-sdk-cpp/releases): "There aren't any releases here"), and is not distributed on PyPI (404) or in Ubuntu 26.04/resolute for any name variant. Because upstream CI is entirely absent (not merely absent for riscv64) and no distribution channel ships this project at all - not even an unpatched distro build - the distribution floor cannot apply, and the base color is orange. The optimization-purpose cap (absent RISC-V code, since the project does contain ARM/Xtensa hand-tuned kernels but none for RISC-V) independently caps at orange as well, so both paths converge on the same result.
- **Pending work that could change the grade:** None identified. No open PRs, no RISE involvement, and no tracking issue exists for a riscv64 port of this specific SDK. The only related upstream activity is in a transitive dependency, TensorFlow Lite Micro, where [PR #3280](https://github.com/tensorflow/tflite-micro/pull/3280) adds RVV kernels for riscv32 (not riscv64) and remains unreviewed since January 2026 - this would not, even if merged, directly change this SDK's own port status without additional integration work.

## 14. Investment Analysis

RISE has not funded or performed any work on this project specifically (confirmed: no RISE blog post, no `riseproject-dev` GitHub org repo, no wheel-builder listing, no RISE runner usage - see Sections 1 and 12). All work items below are therefore unclaimed.

### 14.1 Functional Enablement

The minimum bar for riscv64 to become a recognized target: add a `porting/riscv64` (or generalize `porting/posix`) target, validate the SDK actually builds and runs correctly on riscv64 hardware/QEMU end-to-end (inference correctness against known model outputs), and get this validated in a consumer example repo (`example-standalone-inferencing`) since this SDK is not independently buildable.

### 14.2 Performance Optimization

Would require adding RVV-accelerated NN/DSP kernels analogous to the existing CMSIS-NN/CMSIS-DSP (ARM) and ESP-NN (Xtensa) paths - a substantial undertaking given CMSIS-NN/DSP alone represents ~14MB of hand-tuned ARM kernel source. A more efficient path may be to prioritize RVV kernel work in the upstream TensorFlow Lite Micro dependency (see [PR #3280](https://github.com/tensorflow/tflite-micro/pull/3280), currently riscv32-only) and let this SDK inherit acceleration transitively, rather than duplicating kernel work at the Edge Impulse layer.

### 14.3 CI/CD Infrastructure

Would require building CI from scratch for this repository (none exists for any architecture today), then adding a riscv64 build+test job - a two-stage effort since baseline CI does not exist to extend.

### 14.4 Ecosystem Enablement

Not applicable - Section 10 omitted per instructions; this is a standalone SDK library with no dependent package ecosystem (no PyPI package, no npm package, no plugin/extension ecosystem depending on it).

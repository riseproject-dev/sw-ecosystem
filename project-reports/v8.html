1. Project Overview

V8 is Google’s JavaScript and WebAssembly engine. It is the runtime inside Chromium/Chrome, Node.js, and Deno. V8 is not affiliated with any independent foundation (not OpenJS, not Linux Foundation as a project). It is a Google-owned project under a BSD-style license (site content under CC BY 3.0), governed through the Chromium OWNERS-file model for distributed code review authority, and it runs on Chromium’s own Gerrit/LUCI infrastructure rather than GitHub.

The canonical repository is Google’s internal Gerrit at chromium-review.googlesource.com/c/v8/v8; bugs are tracked at crbug.com (Monorail/Buganizer), not GitHub Issues. The repository at v8/v8 is a read-only mirror: it has zero GitHub Issues for “riscv” or “riscv64” (confirmed by direct search), and the only file under .github/ is mistaken-pull-closer.yml, a bot that auto-closes every pull request opened against the mirror with a message pointing contributors to v8.dev/docs/contribute (Gerrit). Consequently there is no GitHub-native master tracking issue for the riscv64 port; all 913 “riscv”-matching commits found on the main branch are Gerrit CLs that merely appear as mirrored commits.

Committer process (v8.dev/docs/become-committer): 20+ non-trivial patches reviewed by 3 different people, nomination to v8-committers@chromium.org, two committers second it, a 5-business-day objection window, plus a mandatory Security Key. All patches require 2+ committer reviews, one of whom must be an OWNER. Google employees (Googlers) follow a separate, internal onboarding path, not available to external contributors - a structural asymmetry between Google’s internal V8 team and outside contributors such as the RISC-V team.

COMMON_OWNERS (root-level, broad approval authority) lists approximately 38 names, essentially all @chromium.org/@google.com - core governance is Google-dominated. V8’s RISC-V backend itself is community-maintained by engineers at ISCAS (Institute of Software, Chinese Academy of Sciences) / PLCT Lab, with Kasper Lund as an OWNER; Lund’s affiliation moved from Rivos Inc. to Meta during 2025 (a September 2025 commit shows him still as kasperl@rivosinc.com; RISCV_OWNERS now lists kasperl@meta.com). Google does not itself maintain the RISC-V backend.

3. Upstream Support Tier

V8 uses a CI-presence-based support model rather than named tiers. Per v8.dev/docs/ports, ARM is the only officially supported non-x64/IA-32 architecture. MIPS, PPC, s390, RISC-V, LoongArch64, and x87 are each explicitly listed as “not officially supported,” with the uniform policy text: “The [x] team will do the port. Contact/CC the [x] team in the CL if needed.” Contact for RISC-V: v8-risc-v-ports@chromium.org. docs/official-support.md ties “officially supported” to having a CI bot; riscv64 bots exist but run only via software simulator, not real hardware, which further distinguishes it from the officially supported tier.

This means:

  • Google accepts RISC-V patches but does not commit to maintaining the backend.
  • RISC-V breakages introduced by upstream V8 changes are the responsibility of the RISC-V team (ISCAS/PLCT), not Google.
  • There is no SLA, no rollback policy, and no Google engineer designated to own RISC-V CI failures.
  • Approximately one-quarter of all RISC-V V8 commits in the six months prior to the December 2025 RISE post were purely tracking-work for upstream changes, per that post - a recurring maintenance tax borne entirely by the ISCAS team.

4. Technical Architecture and RISC-V-Specific Subsystems

V8 has four JIT tiers (Sparkplug baseline, Maglev mid-tier, Turbofan/Turboshaft optimizing, plus Liftoff for WebAssembly) and a bytecode interpreter. Direct source inspection (shallow clone of v8/v8 at b49c556f, 2026-10-01) confirms 89 RISC-V-specific files across 11 directories, approximately 74,900 lines total, pure C++ using an in-tree hand-written assembler/disassembler - no .S GNU-as files anywhere (src/heap/base/asm/riscv/push_registers_asm.cc is .cc with inline asm volatile, same pattern as arm64/x64). No vfloat32m1_t-style C intrinsics from riscv_vector.h are used for RVV codegen (0 hits); the one place that header is touched is runtime vlenb detection in cpu-riscv.cc.

ISA extensions referenced/used

5. Build System, Cross-Compilation, and Toolchain

V8 uses GN (Generate Ninja) + Ninja, with a secondary/experimental Bazel build (BUILD.bazel, MODULE.bazel). There is no CMakeLists.txt, no BUILDING.md, no INSTALL, and no cmake/riscv64.cmake anywhere in the repository. There are no Dockerfiles anywhere in the repo - confirmed both by a local find and by a GitHub search_code query for riscv64 repo:v8/v8 filename:Dockerfile (0 results).

Convenience workflow (gm):

alias gm=/path/to/v8/tools/dev/gm.py

Caveat, found directly in tools/dev/gm.py (ManagedConfig.get_target_cpu): gm only auto-detects a native host for arm64/arm/loong64/mips64el. There is no riscv64-host branch, so on a typical x64 development machine gm riscv64.release silently falls through to cpu="x64" - producing an x64-hosted simulator build, not a real cross-compiled riscv64 binary, unless GN args are given manually.

Manual GN, native riscv64 cross-compile (from infra/mb/mb_config.pyl bot configs):

gn gen out/riscv64.release --args='target_cpu="riscv64" use_custom_libcxx=false is_clang=false is_debug=false dcheck_always_on=false'
ninja -C out/riscv64.release d8

Debug variant adds is_debug=true v8_enable_backtrace=true v8_enable_slow_dchecks=true v8_full_debug=true.

Manual GN, simulator build (what V8’s own CI actually runs, host x64):

gn gen out/riscv64.release.sim --args='target_cpu="x64" v8_target_cpu="riscv64" is_debug=false dcheck_always_on=false'
ninja -C out/riscv64.release.sim d8

Add v8_enable_pointer_compression=true for the riscv64_pointer_compression CI variant.

use_custom_libcxx=false disables V8/Chromium’s bundled libc++ and falls back to system libstdc++, because no prebuilt libc++ is shipped for riscv64 cross-compilation (same flag used for ppc64 and s390x). v8_riscv_enable_deprecated_riscv32 = false by default in BUILD.gn compiles riscv32 out unless explicitly enabled.

Compiler selection: the 'gcc' mixin in infra/mb/mb_config.pyl sets is_clang=false for native (non-simulator) riscv64 debug/release bots - native riscv64 builds in V8 CI use GCC, not Clang (Clang is used for everything else, including the x64-hosted simulator builds). No minimum GCC or Clang version is declared anywhere in the repository for riscv64; DEPS pins Clang via an opaque CIPD package hash, architecture-generic, not riscv64-specific. The native-riscv64 gcc mixin assumes whatever riscv64 cross-GCC toolchain is already on the builder’s PATH. The sysroot is Debian Trixie for riscv64 (all other architectures use Bullseye) [NEEDS VERIFICATION: this sysroot detail is carried from prior research and was not independently re-confirmed in the current pass], fetched via build/linux/sysroot_scripts/install-sysroot.py --arch=riscv64 since no prebuilt CIPD sysroot exists for riscv64.

The riscv-specific declare_args() defaults gating codegen (riscv_use_rvv, riscv_rvv_vlen, riscv_profile, riscv_use_zba/zbb/zbs/zicond/zicfiss, riscv_code_alignment, riscv_constant_pool_alignment, riscv_use_sv39) live in build/config/riscv.gni, which is not in v8/v8 - it is pinned via DEPS at commit bc0661cf80717e97e1b6868396f61f7f94f2d04a of the separate chromium/src/build.git repo, fetched through gclient sync/depot_tools.

QEMU: no QEMU usage anywhere in the repo for riscv64. The one script with a --use-qemu flag (tools/builtins-pgo/generate.py) explicitly supports only arm/arm64 and errors out ("{cpu} binaries can't be run with qemu") for any other target, including riscv64. V8’s own CI bots for riscv64 run on Ubuntu-22.04 x64 swarming workers, testing the software simulator - not real riscv64 hardware or QEMU userspace emulation.

6. Feature Coverage and Gap Analysis vs arm64 and amd64

6.1 Overall Parity

All four JIT tiers have RISC-V backends at sizes comparable to or larger than arm64/x64 equivalents (Section 4). The December 2025 RISE blog post describes RISC-V as “mostly at feature parity with officially supported architectures like x86_64 and ARM64” and “one of the most green ports” on V8’s buildbots. No numeric cross-architecture benchmark comparison (JetStream, Speedometer, or otherwise) has been published as of this research.

6.2 Float16 / Zvfh

Zvfh detection exists (CpuFeatures probing, commit 2cf1906 “Add zfh/zvfh detect”), but f16x8 Wasm SIMD arithmetic is not yet merged. CL 7953190 implements vfadd/vfsub/vfmul/vfdiv for fp16 under Zvfh. The CL is code-complete and has passed CQ dry-run but is blocked solely on the Gerrit Review-Enforcement requirement: Ji Qiu (RISC-V OWNER) has given +1, no general V8 owner has given the required +2.

6.3 Byte/Halfword Atomics (Zabha)

liftoff-assembler-riscv64-inl.h has TODO(riscv): use Zabha instruction if enabled for byte/halfword atomics, which currently fall back to a slower instruction sequence. No CL implementing Zabha was found in either research pass.

6.4 Instruction Scheduler Latencies

The instruction scheduler’s latency table (instruction-scheduler-riscv.cc) was copied from the MIPS port and does not reflect any real RISC-V microarchitecture; GitHub issue riscv-collab/v8#374 (“Update instruction latencies,” open since 2020-12-31) tracks this. This affects code quality on out-of-order cores.

6.5 Zbb Rotation (rol/ror)

GitHub PRs #93 and #94 (author donebd, 2024-06-03) attempted to add ror/rol to the macro-assembler via the GitHub mirror; both were closed same-day, blocked by the Google CLA bot (the contributor never signed the CLA, so no human review ever occurred - PR #94 appears to be a same-day restart attempt after #93 stalled). No equivalent Gerrit CL was found in either research pass, so Zbb rotation remains absent from the backend. [NEEDS VERIFICATION, single source carried from a prior pass: a separate CL enabling Zba/Zbb/Zbs/Zicond for the rva23u64 profile target was reported but not independently re-confirmed this pass; if real, it would not include the rotation-specific macro-assembler paths regardless.]

6.6 Sub32 / INT_MIN Overflow Bug

CL 7500131 (open since 2026-01-20) attempts to fix handling of Sub32 around INT_MIN/immediate overflow in 32-bit integer subtraction. It has been stalled since January 2026 on an unresolved correctness objection, and no reproducer/test case demonstrating the bug has been provided. This is a latent correctness risk for 32-bit integer subtraction on riscv64.

6.7 Auipc+Jalr to Jal Optimization (stalled)

CL 6874383 (SpacemiT, Zhijin Zeng; open since 2025-08-22, moved to WIP 2026-02-03) replaces 2-instruction auipc+jalr sequences with a single jal where the offset fits. A CQ dry run passed. The CL is stalled on a safepoint-table-integrity concern: changing the physical address of jump instructions breaks the safepoint table’s instruction-offset-to-GC-metadata mapping. A proposed nop+jal fix preserving the 2-instruction slot has been suggested but not yet submitted as a separate CL.

6.8 Zicfiss Shadow Stack

The hardware path in shadow-stack-riscv.cc/.h (45+63 lines) is UNREACHABLE(). Only the simulator path is implemented, gated by V8_ENABLE_RISCV_SHADOW_STACK. No hardware-enabled CFI shadow stack support exists on riscv64 today.

6.9 Simulator Fidelity and Real-Hardware Bugs

The simulator does not faithfully reproduce all hardware behavior. A confirmed case (reported in the December 2025 RISE blog post): vector-register save/restore around calls into C++ code was incorrect, and the bug was found only through testing on physical hardware, not in simulator-only CI - this bug had already shipped past CI before being caught. A second fixed bug of the same class: an atomic jump-table-patching race in Wasm indirect function calls, where a CPU could execute a stale/mismatched auipc/jalr pair during code patching; the fix replaces the two-instruction sequence with an atomic memory load of the target address.

6.10 Performance Optimizations Landed (RISE Dec 2025 post, and recent commits)

  • sh3add (Zba): address-calculation sequences reduced from 4 instructions to 2 in the common case.
  • zext.w (Zba): pointer decompression reduced from 5 instructions to 2 (“a nice and noticeable improvement,” per the authors).
  • Constant-pool emission simplified: moved from interleaved emission to end-of-codegen emission, both simplifying pool logic and preparing for moving constants to a non-executable memory section.
  • Int32MultiplyOverflownBits: peephole optimization using Mul32 + srai(out, out, 32) for Maglev.
  • RVV vector width expanded from 128-bit only to include 256-bit and 512-bit vector CPUs, which was the last piece needed to run the full JetStream suite to completion.
  • Recent correctness fixes landing at a near-daily cadence through late September 2026, including: a register-constraint bit-field overlap bug after an AccessMode field shrink (65b7f9a); ZeroExtendsWord32ToWord64NoPhis handling for atomic loads and kProjection nodes in Turboshaft (91aca67, 6ce3a62); register clobbering in atomic compare-exchange (de0cae9); Liftoff sub-word atomic RMW (d45bc02); incorrect carry in wasm-wide-arith Add128 (b3783c4); out-of-line spill space sizing in RecordSpillsInSafepoint (6b42691); and CompareTaggedAndBranch with relocatable immediates (26e258c).

6.11 Benchmark Data

The only quantitative riscv64 V8 numbers found are from riscv-collab/v8#701 (“Octane failed on Unmatched,” open since 2022-06-30), an Octane run on a SiFive HiFive Unmatched board: Richards 3.96, DeltaBlue 4.47, Crypto 2.64, RayTrace 10.0, EarleyBoyer 18.0, RegExp 4.48, Splay 29.8, SplayLatency 262 - with NavierStokes, PdfJS, and SunSpider all failing (checksum/incorrect-output errors), not merely scoring low. These scores reflect 2022-era immature codegen and active correctness failures; they are not representative of the current port and are an order of magnitude below typical x86/ARM Octane scores of that era. No modern (2024-2026) JetStream or Speedometer score, and no riscv64-vs-arm64/x86_64 numeric comparison, has been published by V8, RISE, or any other source found.

7. CI/CD Infrastructure

7.1 Upstream LUCI CI

V8’s CI runs on Google’s LUCI infrastructure (ci.chromium.org), not GitHub Actions. Direct inspection of v8/v8 confirms there is no .github/workflows/ directory at all - .github/ contains exactly one file, mistaken-pull-closer.yml (a probot config with no on:/jobs:/runs-on: keys, running no code). A grep -ri riscv -r .github returns zero matches. Any claim of GitHub-hosted riscv64 CI for V8 is false as stated; if riscv64 testing exists, it happens entirely outside GitHub.

Three dedicated LUCI builders per infra/testing/builders.pyl run the full test suite via software simulator and pass consistently: “V8 Linux - riscv64 - sim”, “sim - debug”, and “sim - pointer compression”. All run on Ubuntu-22.04 x64 swarming dimensions (target_cpu="x64" v8_target_cpu="riscv64"), not native hardware or QEMU. Corresponding try builders exist (v8_linux64_riscv64_dbg, _rel, _pointer_compression_rel). No native (bare-metal) riscv64 builders exist in upstream V8 CI; native (target_cpu="riscv64") GN configs in mb_config.pyl are present only under developer_default, for local developer use.

12. Objections and Upstream Blockers

Is the upstream maintainer team stable enough to depend on? The functional RISC-V backend is maintained operationally by two ISCAS/PLCT Lab engineers, Yahan Lu and Ji Qiu, plus Kasper Lund (Meta) as a third OWNER. There is no Google commitment to continuity: Google’s stated policy (Section 3) is that RISC-V breakage is the RISC-V team’s responsibility, not Google’s. The approximately 25% upstream-tracking overhead figure quantifies the exposure: roughly one-quarter of all RISC-V V8 effort over a recent six-month window went to chasing upstream changes rather than producing new capability. This is a single-organization concentration risk - if ISCAS deprioritizes V8, the port degrades with each subsequent upstream change, since Google has no internal team positioned to absorb the work.

Does the simulator give adequate confidence for production deployments? No. Simulator-only upstream CI failed to catch a real-hardware vector-register save/restore bug (Section 6.9); it was found only through testing on physical hardware, outside the official CI loop. Organizations deploying V8 on physical RISC-V hardware need their own bare-metal or QEMU validation to catch classes of bugs the simulator cannot.

Is the Sub32 overflow bug (CL 7500131) a production risk? It is a latent correctness risk in 32-bit integer subtraction around INT_MIN boundary values. The fix has been stalled with an unresolved objection since January 2026, and no test case demonstrating a failure has been contributed, so the practical risk cannot be quantified without a reproducer. This warrants direct investigation before relying on V8 for arbitrary JavaScript execution on riscv64.

Is there a path to official Google support for riscv64? Data not available: no public statement from Google’s V8 team committing to officially support riscv64 was found in either research pass. Official support (per docs/official-support.md) is tied to CI-bot presence and is implicitly reserved for architectures Google itself runs in production; no evidence was found that Google runs RISC-V hardware in production at a scale that would motivate elevating riscv64’s tier.

What is RISE’s actual involvement? RISE Project’s only documented touchpoint with V8 is a single blog post, “A Glimpse Into V8 Development for RISC-V” (published 2025-12-09, authored by Florian Loitsch, Ji Qiu, Kasper Lund, Yahan Lu, and Zhijin Zeng). Of the 35 posts on the RISE blog, only this one mentions V8. There is no RISE GitHub/GitLab repository for V8 (the full 26-repo riseproject-dev org listing contains none), no evidence V8 CI uses RISE RISC-V Runners, and V8 is absent from the RISE Python wheel_builder’s 87-package list. The post itself does not claim RISE funded the described work - it reads as ecosystem reporting on community engineering progress, not a RISE-commissioned project. RISE membership is organizational, not project-level: V8 itself is not a RISE member or project. The connection to RISE is indirect, through Google (a RISE Premier Member, which owns V8 overall) and ISCAS (a RISE General Member, whose engineers - Ji Qiu and Yahan Lu - are the two primary riscv64 maintainers).

Are there performance numbers for RISC-V vs. ARM64 or x86-64? No cross-architecture numeric benchmark comparison (JetStream, Speedometer, or any other suite) is publicly available. JetStream suite completion on RISC-V is documented as a capability milestone, but no score is published anywhere found, by V8, RISE, SpacemiT, or any independent source.

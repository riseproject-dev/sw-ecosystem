# RISC-V Ecosystem Status Reports -- Operator Guide

This repository contains RISC-V ecosystem status reports for the open-source
projects. All reports are generated by running a deep-research workflow via
Claude Code.

---

## Quick Start: Generate a Single Report

Look the project up in `project-reports/scope.yml` and pass its fields as the workflow args. The
`repo` and `home` fields map straight through; the script derives the output path
`project-reports/<slug>.md` from the name.

```
Workflow({
  args: [{"name": "GDB",
          "repo": "https://sourceware.org/git/binutils-gdb.git",
          "home": "https://www.gnu.org/software/gdb/"}],
  scriptPath: "/abs/path/to/.prompts/riscv-report.js"
})
```

This writes to `project-reports/gdb.md`. To override the path, add an absolute `"slug"`
field to the args object to output to `project-reports/<slug>.md`.

After the workflow completes, write the report and commit:

```python
# Extract report from workflow output
import json, os
data = json.load(open("<task-output-file>"))
item = data["result"][0]
open(item["file"], "w", encoding="utf-8").write(item["report"])

# Verify: file size > 10 KB and title heading matches
print(os.path.getsize(item["file"]), "bytes")
print(next(l for l in open(item["file"]) if l.startswith("# ")))
```

```bash
git add <file> && git commit -m "Add <Name> RISC-V ecosystem status report"
```

## Project List

The canonical list of projects and their metadata (name, repo URL, home URL) is in
**`project-reports/scope.yml`** at the repo root. That file is the single source of truth; do not
duplicate it here. Each entry has three fields:

```yaml
- name: GDB
  repo: https://sourceware.org/git/binutils-gdb.git
  home: https://www.gnu.org/software/gdb/
```

Each entry maps to one workflow invocation. The workflow args are derived as follows:

| Arg | Source in `project-reports/scope.yml` |
|-----|-----------------------|
| `name` | The `name:` field, verbatim |
| `repo` | The `repo:` field (absent for projects with no public repo, e.g. Geekbench) |
| `home` | The `home:` field |
| `slug` | Not in `project-reports/scope.yml` -- derived by the script as `project-reports/<slug>.md` |

The output slug is the lowercased name with spaces, dots, and slashes replaced by
hyphens: `name.toLowerCase().replace(/[\s.\/]+/g, '-')`. So "Apache Flink" ->
`project-reports/apache-flink.md`, "Open vSwitch" -> `project-reports/open-vswitch.md`,
"GDB" -> `project-reports/gdb.md`. To override, pass an absolute `slug` arg explicitly.

Example: for the `GDB` entry above:

```js
{
  "name": "GDB",
  "repo": "https://sourceware.org/git/binutils-gdb.git",
  "home": "https://www.gnu.org/software/gdb/"
}
// -> writes project-reports/gdb.md
```

To get the list of remaining projects (those without a status report yet):

```bash
# Reports already generated
ls project-reports/*.md 2>/dev/null | sed 's|.*/||' | sort > /tmp/done.txt

# All expected report files, derived from project-reports/scope.yml names
grep '^- name:' project-reports/scope.yml | sed 's/^- name:[[:space:]]*//' | \
  sed 's/[ ./]\+/-/g' | tr '[:upper:]' '[:lower:]' | \
  sed 's|$|.md|' | sort > /tmp/expected.txt

comm -23 /tmp/expected.txt /tmp/done.txt   # projects still missing a report
```

## Generating All Reports in Sequence

Run one project at a time in the order they appear in `project-reports/scope.yml`.
Do not launch the next until the previous is committed.

### Workflow args format

```js
{
  "name": "<ProjectName>",             // project-reports/scope.yml: name (display name)
  "repo": "<upstream-repo-url>",       // project-reports/scope.yml: repo (GitHub or non-GitHub; omit if none)
  "home": "<project-homepage-url>"     // project-reports/scope.yml: home (for governance section)
}
```

The script derives the output path as `project-reports/<slug>.md`. Add an optional
`"slug"` field only when you need to override that default.

## Operational Rules

### One project at a time

**Never launch two workflows concurrently.** Each workflow runs 16 agents that each
make dozens of API calls. Two concurrent workflows will immediately saturate the
rate limit and both will stall with agents frozen at 3 lines.

### GitHub vs non-GitHub projects

The workflow script (`.prompts/riscv-report.js`) auto-detects GitHub by parsing the URL.
- GitHub projects get GitHub MCP tool calls (issues, PRs, code search, file contents)
- Non-GitHub projects (sourceware.org, kernel.org, googlesource.com) get WebSearch + WebFetch

Non-GitHub projects take longer because they rely on web scraping rather than the
structured GitHub API. sourceware.org and kernel.org often return Anubis bot challenges,
so the search agents spend extra retries.

### Rate limiting

The model rate limit is per-minute. Each workflow burns roughly 600k-700k tokens across
all 16 agents. When a rate limit is hit:

1. The workflow stalls -- agents freeze mid-run with no new journal entries
2. The workflow process eventually dies, leaving the journal with STARTED but no RESULT
3. The output file is empty (0 bytes)

**Recovery procedure:**
1. Check that the task is gone: `TaskStop({task_id: "..."})` will return "no task found"
2. Resume with `Workflow({args: [...], resumeFromRunId: "wf_...", scriptPath: "..."})`
   - Pass the SAME args as the original call
   - The `resumeFromRunId` causes completed agents to return cached results instantly
   - Only the remaining agents run live
3. If the resumed workflow also stalls, wait 15 minutes then resume again
4. Repeat until all 16 agents complete

**Checking workflow progress** while it runs:

```python
import json
base = '/abs/path/.claude/projects/<session>/subagents/workflows/<wf_id>'
objs = [json.loads(l) for l in open(f"{base}/journal.jsonl").read().strip().split('\n')]
started = sum(1 for o in objs if o["type"] == "started")
done = sum(1 for o in objs if o["type"] == "result")
print(f"{started} started, {done} results")
```

The journal path is printed when you call `Workflow(...)`. Format:
`/abs/path/to/.claude/projects/<session-hash>/subagents/workflows/<run-id>/`

### Reading workflow output

```python
import json, os

# The output file path is in the task notification
with open("<output-file-path>") as f:
    data = json.load(f)

item = data["result"][0]
status = item.get("status", "OK")   # "FAILED" or absent (=OK)
report = item.get("report", "")
filepath = item["file"]

print(f"Status: {status}, chars: {len(report)}")

if status != "FAILED" and len(report) > 5000:
    with open(filepath, "w", encoding="utf-8") as f:
        f.write(report)
    print(f"Written: {os.path.getsize(filepath)} bytes")
    print(next(l for l in open(filepath) if l.startswith("# ")))   # verify title heading
```

### Verification criteria

Before committing, verify:
1. File size > 10 KB -- target for a full report
2. File size > 5 KB minimum -- below 5 KB is likely partial/stub, do not commit
3. First line after front-matter is exactly `# <ProjectName>`

If any check fails: do NOT commit. Note the failure, continue with the next project,
come back later with a fresh workflow run for the failed one.

### Commit format

```bash
git add <directory>/<project>.md
git commit -m "Add <Name> RISC-V ecosystem status report

Co-Authored-By: Claude Sonnet 4.6 (1M context) <noreply@anthropic.com>"
```

## Workflow Internals

The workflow script (`.prompts/riscv-report.js`) runs four phases sequentially,
16 agents total:

| Phase | Agents | What they do |
|-------|--------|-------------|
| Search | 8 | Issues/PRs, CI config, packages, RISE, arch code, governance, deps, perf/bugs |
| Fetch | 4 | Deep reads of top issues, PR merge verification, build docs, RISE details |
| Verify | 3 | Adversarial CI check, adversarial package check, arch code completeness |
| Synthesize | 1 | Writes the full report text from all findings |

Phases are sequential (each agent awaits the previous). This prevents rate limit
stampedes. The Synthesize agent receives up to 90,000 characters of research
context and writes the report as its final text output (no Write tool call).

The main session then writes the returned `report` string to disk via Python.

### Abort threshold

If Phase 1 search returns fewer than 1000 total characters across all 8 agents,
the workflow aborts with `status: "FAILED"`. This happens when:
- The rate limit is already saturated at launch
- Tools are unavailable
- The project URL is wrong

## Known Issues from the 2026-06 Session

### sourceware.org Anubis protection

All sourceware.org URLs (glibc, GDB, Valgrind, binutils) are protected by the
Anubis bot challenge system. Web fetch agents see "Access Denied: error code
9e4edb5b6b850c41". Workarounds:
- GitHub mirrors (bminor/glibc, T-J-Teru/binutils-gdb) are accessible
- GitLab mirrors (gitlab.com/gnutools/binutils-gdb) are accessible
- The Buildbot API at builder.sourceware.org is directly accessible
- PyPI, Debian tracker, and Arch Linux mirror remain accessible

Reports for sourceware.org projects will have gaps in Bugzilla data but are
otherwise complete from GitHub mirrors and mailing list archives.

### open-telemetry org

The `url` for OpenTelemetry should be `https://github.com/open-telemetry` (the
organization), not a specific repo. The workflow handles org-level URLs for
projects that span multiple repos.

### Android non-GitHub repos

ART (`android.googlesource.com`) and Android Bionic are non-GitHub. The workflow
uses WebSearch + WebFetch for these. Android Review (Gerrit) changes are fetched
via direct URL patterns like `android-review.googlesource.com/c/platform/art/+/<id>`.

### Workflow empty output (0-byte output file)

**Symptom:** Workflow task notification arrives, but the output file is 0 bytes.

**Cause A:** The workflow was killed by the session being interrupted (e.g., user
presses Ctrl-C or closes the terminal). The journal has only `STARTED` entries
with no matching `RESULT` entries. Agents at 3 lines each = killed early.

**Cause B:** Rate limiting caused agents to stall mid-run for 17+ hours. The
workflow process eventually dies from the underlying infrastructure timeout.

**In both cases:** Resume with `resumeFromRunId` and pass args. The journal
preserves all completed agent results. The resume only re-runs the missing agents.

### Rate limit pattern

Rate limits hit predictably around agent 11-12 of 16. The symptom is `started`
count stays at N while `result` count stays at N-2 for many minutes. Wait 15
minutes and resume. Two resumes are usually sufficient to clear the queue.

### SpiderMonkey and Firefox share a repo

Both `SpiderMonkey` and `Firefox` use `url: https://github.com/mozilla/gecko-dev`.
The workflow script is the same -- the `name` and `home` args determine which
project the synthesize agent writes about. Run them as separate workflow calls
with different `name` values.

## Updating Existing Reports

When refreshing a report (every ~6 months), use the same workflow call with the
same args. The synthesize agent will write a fresh report from its live research.
After writing, diff against the previous version to confirm no regressions in
factual accuracy, then commit.

## Session Reproducibility Checklist

To reproduce the 2026-06 session from scratch on a new machine or after context loss:

1. Clone the repo: `git clone <repo>`
2. Verify the workflow script exists: `prompts/project-report/project-report-workflow.js`
3. Create the output directory if missing:
   ```bash
   mkdir -p project-reports
   ```
4. Set the working directory to the repo root in Claude Code
5. Read `project-reports/scope.yml` to get the project list and derive workflow args
6. Find which reports are missing (see the `comm` command in the Project List section)
7. Run one project at a time
8. Monitor every 5 minutes using the journal Python snippet
9. Wait 15 minutes and resume on any rate limit stall
10. Write, verify (>5 KB, correct first line), commit after each completion
11. Proceed to the next project only after committing

Total expected runtime: ~2 hours per project (including rate-limit waits).
Total for all projects: ~5-6 days of unattended operation.

# RISC-V Ecosystem Status Project Report -- Operator Guide

This repository contains RISC-V ecosystem status reports for open-source projects. Every report is
generated by the research workflow described here; reports are never written or patched by hand.

---

## Quick Start: Generate a Single Report

Dispatch the `project-report` GitHub workflow with the project's name as spelled in `projects.yml`:

```bash
gh workflow run project-report.lock.yml -f project="GDB"
```

or use Actions -> the project report workflow -> Run workflow. The run researches the project and
opens a pull request, as the riseproject-dev app, containing `project-reports/<slug>.md` and any
`projects.yml` changes. Review the pull request and merge it.

If the project already has a report, the run is a full rewrite of it. If the name is not in
`projects.yml`, the run adds a registry entry for it.

---

## How a Run Works

| Stage | What happens |
|-------|--------------|
| Resolve | The agent looks the project up in `projects.yml` and derives the report path. |
| Research | The agent launches `project-report-workflow.js` and waits for it. |
| Assemble | The agent builds the report file from the script's result and updates `projects.yml`. |
| Check | Structure, dependency names and process narration are checked. |
| Publish | One pull request with one commit is opened. |

The pieces:

- **`.github/workflows/project-report.md`** -- the agentic workflow: its frontmatter (engine, model,
  tools, extensions, credentials) and the prompt the agent follows. `project-report.lock.yml` is
  generated from it by `gh aw compile project-report`; commit both after any frontmatter change.
- **`project-report-workflow.js`** -- the orchestration script. It runs about twenty steps in
  sequence, each in its own sub-agent, through the pi-subagents extension:

  | Phase | Steps | What they do |
  |-------|-------|--------------|
  | Search | 8 | Issues/PRs, CI config, packages, RISE, arch code, governance, deps, perf/bugs |
  | Fetch | 4 | Deep reads of top issues, PR merge verification, build docs, RISE details |
  | Verify | 3 | Adversarial CI check, adversarial package check, arch code completeness |
  | Synthesize | 3 or 4 | Reads the existing report (rewrite only), extracts the direct dependencies and resolves them against `projects.yml`, grades the readiness color, writes the report |

- **`agents/report-researcher.md`** -- the agent every step runs as: its tools, and the mapping from
  the tool names used in the step prompts to the tools available at run time.
- **`project-report.md`** -- the report template and research instructions.
- **`skills/project-color-coding/SKILL.md`** -- the color model used by the grading step.

### Script arguments and result

| Arg | Source |
|-----|--------|
| `name` | The `name:` field in `projects.yml`, verbatim |
| `repo` | The `repo:` field (absent for projects with no public repo, e.g. Geekbench) |
| `home` | The `home:` field |
| `reportDate` | Today's date, `YYYY-MM-DD` |
| `registryPath` | Absolute path to `projects.yml` |
| `existingReportPath` | Absolute path to the current report; only for a rewrite |
| `reportBodyPath` | Absolute path where the synthesized report body is saved |
| `slug` | Optional override of the derived slug |

The output slug is the lowercased name with spaces, dots, and slashes replaced by hyphens:
`name.toLowerCase().replace(/[\s.\/]+/g, '-')`. So "Apache Flink" ->
`project-reports/apache-flink.md`, "Open vSwitch" -> `project-reports/open-vswitch.md`.

The script returns a one-element array:
`{ name, file, frontmatter, bodyPath, reportChars, totalChars, new_registry_entries }`. The report
is `frontmatter` followed by the content of `bodyPath` from its first `# ` heading. The script
builds the frontmatter itself, from the dependencies and color it computed, so the dependency names
always match the registry. Without `reportBodyPath`, the result carries the whole text as `report`
instead.

If the Search phase returns fewer than 1000 characters in total, the script stops and returns
`status: "FAILED"`. That means the tools were unavailable or the project URL is wrong; no pull
request is opened.

## Project List

The canonical list of projects and their metadata (name, repo URL, home URL) is in
**`projects.yml`** at the repo root. That file is the single source of truth; do not duplicate it
here. Each entry has `name`, `repo`, `home`, and optionally `report:` (path to an existing
per-project report) and `synonyms:` (alternate names used in the dependency graphs):

```yaml
- name: GDB
  repo: https://sourceware.org/git/binutils-gdb.git
  home: https://www.gnu.org/software/gdb/
  report: project-reports/gdb.md
```

An entry that already carries a `report:` field has a report; entries without one are the
candidates still needing a report. To list them (requires a YAML parser; the registry carries
multi-line entries, so a line grep is not reliable):

```bash
python3 - <<'PY'
import yaml
reg = yaml.safe_load(open('projects.yml'))
missing = [e['name'] for e in reg if not e.get('report')]
print(f"{len(missing)} projects with no report:")
for n in sorted(missing, key=str.lower):
    print(" ", n)
PY
```

Many `projects.yml` entries are dependency-graph-only projects (libraries pulled in by the stack
reports) that are not necessarily report candidates; use judgment about which are worth a full
per-project report.

## Reviewing a Report Pull Request

Before merging, check:

1. File size > 10 KB -- the target for a full report. Below 5 KB is a stub; do not merge.
2. The frontmatter is followed by the dependency-graph include line and then `# <ProjectName>`.
3. Every `dependencies:` entry in the frontmatter has a matching `projects.yml` entry, either
   pre-existing or added in the same pull request. `_plugins/dependency_graph_generator.rb`
   hard-fails the site build otherwise.
4. The grade in Section 13 rests on evidence the report actually cites. If the grade-deciding
   evidence is marked `[NEEDS VERIFICATION]`, re-run instead of merging.
5. The report does not narrate the research process (tools, agents, access errors, earlier
   versions).

### New registry entries

The dependency step resolves every direct dependency against `projects.yml` and reports the ones it
did not find. The run adds one entry for each. The resolution is best-effort, so check for a
near-miss spelling of a project that is already listed under a different name; if so, drop the new
entry and add the spelling to the existing entry's `synonyms:` instead.

Each new entry is its own `- name: / repo: / home:` block (no `report:` or `synonyms:`), in
case-insensitive alphabetical order. `projects.yml` is hand-formatted with a header comment and
blank-line-separated entries: never re-serialize the whole file.

```yaml
- name: OpenSK
  repo: https://github.com/google/OpenSK
  home: https://github.com/google/OpenSK
  report: project-reports/opensk.md

- name: OpenSSH
  repo: https://github.com/openssh/openssh-portable
  home: https://www.openssh.com/

- name: OpenSSL
  repo: https://github.com/openssl/openssl
  home: https://www.openssl.org/
  report: project-reports/openssl.md
```

## Updating Existing Reports

There is only one way to refresh a report: a full rewrite. Dispatch the workflow again for the same
project. The Synthesize phase reads the existing report and merges it with a full fresh research
pass into one standalone report; nothing in the output references a previous version, and there is
no Updates section to append to.

Never hand-append a changelog-style entry to a report instead of running this.

## Known Source Quirks

### sourceware.org Anubis protection

All sourceware.org URLs (glibc, GDB, Valgrind, binutils) are protected by the Anubis bot challenge
system, and fetches see "Access Denied". Workarounds:

- GitHub mirrors (bminor/glibc, T-J-Teru/binutils-gdb) are accessible
- GitLab mirrors (gitlab.com/gnutools/binutils-gdb) are accessible
- The Buildbot API at builder.sourceware.org is directly accessible
- PyPI, Debian tracker, and Arch Linux mirror remain accessible

Reports for sourceware.org projects will have gaps in Bugzilla data but are otherwise complete from
GitHub mirrors and mailing list archives.

### open-telemetry org

The `repo` for OpenTelemetry should be `https://github.com/open-telemetry` (the organization), not
a specific repo. The script handles org-level URLs for projects that span multiple repos.

### Android non-GitHub repos

ART (`android.googlesource.com`) and Android Bionic are non-GitHub. The script uses web search and
page fetches for these. Android Review (Gerrit) changes are fetched via direct URL patterns like
`android-review.googlesource.com/c/platform/art/+/<id>`.

### SpiderMonkey and Firefox share a repo

Both `SpiderMonkey` and `Firefox` use `repo: https://github.com/mozilla/gecko-dev`. The `name` and
`home` determine which project the report is about. Run them as separate dispatches.

## Changing the Workflow

- **Prompt or step changes** (the Markdown body of `project-report.md` under `.github/workflows/`,
  the script, the agent definition): commit the change; no compile is needed.
- **Frontmatter changes** (engine, model, tools, extensions, permissions): run
  `gh aw compile project-report` and commit the regenerated lock file with the source. This
  repository only allows actions pinned to a full commit SHA, so compile with the gh-aw setup action
  pinned, for example
  `gh aw compile project-report --action-mode action --action-tag <commit-sha-of-the-gh-aw-actions-release>`.
- **Testing a change**: push it to a branch and dispatch the workflow on that branch
  (`gh workflow run project-report.lock.yml --ref <branch> -f project=<name>`). The run opens a
  real pull request; close it without merging.
